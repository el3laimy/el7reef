# محضر مجلس تطوير الحريف للشباب والسوق المصري

> **نوع الوثيقة:** محضر بحث وقرار تابع للخطة الأم، وليس Roadmap أو Backlog أو خطة نشطة مستقلة. الحالة والأولوية والتنفيذ تحكمها فقط `docs/core/00_Master_Product_Development_Plan.md`&rlm;.

**التاريخ:** 29 يوليو 2026

**آخر مراجعة للتكوين:** 8 أغسطس 2026

**النطاق:** Android، نواة مجد البطولات، والسوق المصري للبالغين من الأجيال الشابة

**حالة المجلس:** القرارات معتمدة للتخطيط؛ الفرضيات السوقية لا تصبح حقيقة إلا بعد البحث والـPilot&rlm;.

## 1. تكوين المجلس وسلطة القرار

المقاعد التالية تمثل **اختصاصات يجب أن تكون حاضرة في القرار**، ولا تفترض فريقًا كبيرًا أو موظفًا متفرغًا لكل مقعد. يمكن لشخص مؤهل أن يغطي أكثر من اختصاص، لكن لا يجوز أن ينفذ تغييرًا حساسًا ثم يمنحه اعتماد الأمن أو الجودة أو القانون بنفسه.

### 1.1 الاختصاصات الدائمة المتاحة للمجلس

لا تجتمع كل هذه المقاعد في كل قرار. يتكون **مجلس القرار الأساسي** من كبير المجلس، ورئيس المشروع، وكبير الهندسة، ومصمم المنتج، وQA، وينضم قائد عمليات الـPilot أثناء البحث الميداني والتشغيل الحقيقي. تُستدعى بقية الاختصاصات بحسب أثر القرار، بينما يظل خبراء البوابات مستقلين عن التنفيذ.

| المقعد | المسؤولية | ما لا يملكه منفردًا |
| :--- | :--- | :--- |
| كبير المجلس وخبير المنتج | حسم الرؤية والتعارضات وقرارات `Continue / Adjust / Kill`&rlm; | تجاوز بوابات الأمن أو نشر Firebase أو توسيع V1 بلا تذكرة |
| رئيس المشروع | إدارة المحفظة والسعة والتبعيات والأدلة وحالة الخطة الأم | تغيير الرؤية أو اعتبار تقدير زمني وعدًا |
| وكيل دراسة السوق المصري | فصل الحقيقة عن الفرضية وتصميم البحث الميداني | تعميم نتائج رقمية على كل الشباب أو اعتبار الوصول الإعلاني مستخدمين نشطين |
| وكيل التسويق والنمو | التموضع والاكتساب والاحتفاظ وحساب اقتصاد التجربة | شراء تنزيلات قبل إثبات التفعيل |
| خبير السوشيال ميديا | وظيفة كل قناة والمحتوى والموافقة وقياس التحويل | إنشاء Feed داخل التطبيق أو اعتبار المشاهدة نجاحًا نهائيًا |
| المدير الإبداعي والهوية الرياضية | تماسك الشعار والهوية وبطاقات المفاخرة والحركة والصوت وأصول المتجر والسوشيال | إضافة لقب أو إنجاز أو رقم غير صادر عن مصدر حقيقة |
| مصمم المنتج وباحث الاستخدام | الرحلات والحالات واللغة والوصول والاختبار في ضوء النهار وبيد واحدة | التضحية بالوضوح من أجل الإبهار أو اعتماد تنفيذه البرمجي منفردًا |
| مهندس Flutter Frontend | تنفيذ الواجهات والحالة والأداء وRTL وعقود الوصول على Android | تغيير قرار المنتج أو مصدر البيانات أو اعتماد جودة عمله منفردًا |
| كبير الهندسة ومعماري Flutter/Firebase | عقود Flutter وFunctions وFirestore وADRs والتوافق الخلفي والأداء والكلفة التقنية | تجاوز AppSec أو QA أو الموافقة المالكة على النشر |
| مهندس Backend/Firebase | تنفيذ Functions وRules والمعاملات والفهارس والمهاجرات المأمونة | اعتماد أمن أو قياس التغيير الذي نفذه بنفسه |
| خبير تحليلات المنتج وتصميم التجارب | قاموس القياس والـFunnel والـbaseline وحجم العينة ومعايير الإيقاف وصحة الاستنتاج | جمع PII أو توسيع Telemetry والاحتفاظ دون مراجع هندسة الخصوصية وAppSec |
| الخبير النفسي السلوكي | الدوافع والكرامة والثقة ومنع الأنماط المضللة | تشخيص المستخدمين أو تصنيفهم نفسيًا من سلوكهم |
| خبير تشغيل البطولات والتحكيم الشعبي | واقعية المجموعات والجولات وكسر التعادل وBYE والترجيح والاعتماد والنزاعات تحت ضغط الملعب | توسيع النطاق أو تغيير قواعد بطولة قائمة بلا قرار موثق |
| معماري الاختبار وضمان الجودة | استراتيجية الاختبار والانحدار والأجهزة الواقعية وتوصية الإصدار وقرار الإيقاف | تمرير فشل حرج لأن المتوسط العام جيد أو اعتماد ميزة كتب اختباراتها وحده |
| مسؤول نزاهة المنصة والثقة والسلامة | انتحال الهوية وClaim الاحتيالي وإساءة المنظم وUGC، وسياسات التبليغ والحظر والإزالة والاستئناف وسلامة الشباب | حسم نزاع رياضي أو قانوني منفردًا، أو تنفيذ إجراء حساس ثم اعتماد نزاهته بنفسه |
| مسؤول تشغيل المجتمع والدعم | استقبال مشكلات المنظمين، تصنيف الحوادث، Moderation SLA، وإغلاق حلقة التعلم من الـPilot | كشف بيانات مستخدم أو حسم نزاع رياضي أو قانوني منفردًا |
| قائد عمليات الـPilot ونجاح المنظم | تجنيد وتأهيل منظمي دفعات `2 → 3 → 5`، وقائمة الجاهزية، وتنسيق يوم المباراة، وسجل التدخلات اليدوية ودليل ما بعد البطولة | تغيير نطاق V1 أو قواعد البطولة أو المقاييس، أو إعلان نجاح التجربة أو الإذن بالنشر منفردًا |

### 1.2 خبراء بوابات إلزاميون

هؤلاء لا يحتاجون مقعدًا دائمًا في كل اجتماع، لكن لا تمر بوابتهم دون توقيع مستقل موثق:

| الخبير | البوابة الملزمة | سلطة الإيقاف |
| :--- | :--- | :--- |
| مراجع AppSec مستقل | إغلاق W1/W2، وأي تغيير Auth أو Rules أو Functions أو Storage أو Claim أو Migration | أي High/Critical، أو تسريب PII، أو authorization regression، أو غياب rollback مأمون |
| مراجع هندسة الخصوصية وحوكمة البيانات | W2 وحذف الحساب وAnalytics وأي SDK أو Storage أو schema/backfill/migration، ثم مطابقة سياسة الخصوصية وPlay Data Safety مع الـAAB قبل `ELR-REL-507` | تدفق PII غير معلوم، أو تسريب public projection، أو حذف/احتفاظ غير قابل للاختبار، أو اختلاف الإفصاح عن السلوك الفعلي |
| مستشار قانوني مصري للمنتجات الرقمية وحماية البيانات وحقوق المحتوى | الخصوصية وData Safety والحذف والاحتفاظ وUGC والشعارات والصور والقُصّر قبل Closed Testing أو النشر المعني | عدم الامتثال أو غياب أساس قانوني أو موافقة أو ترخيص صالح |
| خبير Cloud Operations وSRE/FinOps | Backup/restore وrollout/rollback والمراقبة والاستجابة للحوادث والميزانيات قبل نشر Firebase | غياب الاستعادة أو الرصد أو rollback مجرّب أو سقف تكلفة معلوم |
| مهندس Android/Play Release | Signing وAAB وPlay App Signing وApp Links وتوافق Gradle/Kotlin والاعتماديات قبل Closed Testing والإنتاج | غياب توقيع صحيح أو تطابق إعدادات الإنتاج أو اجتياز بوابات Play |
| مراجع الوصول وأداء Flutter | W3 و`ELR-REL-506` على TalkBack وtext scale والأجهزة المتوسطة والمنخفضة وProfile Mode | عجز المستخدم عن إكمال مهمة حرجة أو تجاوز حدود الأداء المعتمدة |
| مراجع المحتوى العربي وRTL/Content Design | W3 وأي Claim أو نزاع أو موافقة UGC أو نص Play: سلامة المعنى العربي، الاتساق المصري المحترم، وخلط العربية والأرقام والروابط دون التباس | موافقة أو حالة حساسة مبهمة، أو نص يقلب المعنى/الاتجاه، أو قص يمنع إتمام مهمة حرجة |
| مراجع موثوقية Android للشبكة الضعيفة وOffline UX | W3 و`ELR-REL-504/506`: انقطاع الشبكة، الاستئناف، stale/cached state، وإعادة المحاولة وprocess death على جهاز فعلي | ازدواج عملية حساسة أو فقد نتيجتها، أو عرض بيانات قديمة كحقيقة حديثة، أو تعطل استعادة المهمة بعد الانقطاع |

### 1.3 تعريف سلطات الاختصار

- يعني `OWNER` مالك المنتج والحسابات الخارجية، وهو وحده يأذن بالنشر أو الإنفاق أو الالتزام القانوني بعد اكتمال التوقيعات المطلوبة.
- يعني `Product` كبير المجلس وخبير المنتج أو مفوضًا مسمى منه، ويملك النطاق والأولوية لا تجاوز البوابات.
- يعني `ENG` كبير الهندسة، ويملك القرار التقني والتنسيق بين Frontend وBackend لا اعتماد أمن عمله منفردًا.
- يعني `QA` معماري الاختبار وضمان الجودة، ويملك توصية الإصدار ووقفه عند الـblockers وفقد البيانات.
- يعني «المالك» داخل تذاكر الخطة الأم مالك التسليم وجمع الدليل؛ لا ينقل إليه وحده سلطة قبول النطاق. لذلك تظل تذاكر W3 لدى `ENG + QA` للتسليم، بينما يقبل `Product` النتيجة الوظيفية.
- عند تعارض `Product` و`ENG` و`QA`، يحسم كبير المجلس اتجاه المنتج فقط؛ يأذن `OWNER` بالاستمرار التشغيلي أو النشر أو الإنفاق بعد اكتمال البوابات، ولا يملك أي منهما إسقاط Stop-ship أمنيًا أو قانونيًا أو فشل QA حرجًا.

يُعامل «Millennial» و`Gen Z` كخلفية عمرية واسعة، لا كـpersona أو وسيلة تخصيص. المنتج يصمم حسب **المهمة والسياق**: منظم تحت ضغط الملعب، قائد يبني هوية فريق، لاعب يريد إنجازًا موثقًا، ومشاهد وصل من رابط.

## 2. عقد الأدلة

### 2.1 حقائق مفيدة، مع حدودها

- بلغ عدد المصريين من 18 إلى 29 عامًا نحو 21.1 مليون في يناير 2024 وفق [بيان CAPMAS](https://www.capmas.gov.eg/Admin/News/PressRelease/202491110200_%D8%A7%D9%84%D9%8A%D9%88%D9%85%20%D8%A7%D9%84%D8%B9%D8%A7%D9%84%D9%85%D9%89%20%D9%84%D9%84%D8%B4%D8%A8%D8%A7%D8%A8.pdf)&rlm;.
- قدّر [تقرير Digital 2026 لمصر](https://datareportal.com/reports/digital-2026-egypt) مستخدمي الإنترنت بنحو 98.2 مليون في أكتوبر 2025، وذكر 51.6 مليون **هوية** استخدام اجتماعي. أرقام المنصات في التقرير وصول إعلاني محتمل، وليست MAU أو أفرادًا فريدين.
- سجّل [الجهاز القومي لتنظيم الاتصالات](https://www.tra.gov.eg/en/ntra-releases-internet-usage-index-within-single-day-in-ramadan-of-2024/) 40 مليون مستخدم لخدمات الدردشة المجمعة في يوم القياس برمضان 2024. الرقم لا يثبت استخدام WhatsApp منفردًا.
- تظهر بيانات [UNICEF Egypt 2024](https://www.unicef.org/egypt/media/12431/file/SitAn%20of%20Children%20and%20Adolescents%20in%20Egypt%202024_Eng.pdf) فروق اتصال بين الحضر والريف والصعيد، لكنها تعتمد في بعض مؤشرات الشباب على مسح 2021؛ لذلك توجه الاختبار ولا تصف 2026 وصفًا حيًا.
- تشير [بيانات StatCounter لمصر](https://gs.statcounter.com/os-market-share/mobile-per-country/egypt) إلى هيمنة Android على حركة الويب المحمولة المقاسة، لكنها عينة حركة وليست تعداد أجهزة. يظل قرار Android أولًا صحيح الاتجاه ويحتاج اختبارًا على أجهزة منخفضة ومتوسطة.
- تبين [إرشادات UNICEF Egypt](https://www.unicef.org/egypt/protecting-children-cyberbullying-internet-safety) أن الصور والمحتوى المسيء والبيانات المنشورة قد تصبح أدوات للتنمر. هذا يجعل كرامة اللاعب والموافقة جزءًا من المنتج، لا بندًا قانونيًا لاحقًا.

### 2.2 فرضيات لم تثبت بعد

- أن WhatsApp هو أفضل قناة تحويل للحريف، رغم اتساقه مع واقع المنتج الحالي.
- أن منظم الملعب المتكرر هو أقل قناة تكلفة وأكثرها احتفاظًا.
- أن بطاقة MVP الشخصية تنتج فتح روابط أكثر من Match Recap الجماعي.
- أن QR بجوار الملعب يحول المشاهد إلى Claim أو متابعة.
- أن المنظم سيكرر البطولة خلال 30 يومًا؛ دورة البطولات الفعلية قد تكون أطول.

لا تتحول هذه الفرضيات إلى أرقام متجر أو عرض استثماري قبل Evidence ميداني.

## 3. الجولة الأولى: مواقف اللجان

### 3.1 السوق والتسويق

يرى الوكيل أن العميل الأول هو المنظم المتكرر، وأن اللاعب صاحب الإنجاز هو مضاعف الانتشار. المنافس الحقيقي ليس تطبيق نتائج آخر فقط، بل الورق ورسائل الجروب والصور اليدوية. التموضع الذي يحافظ على الحقيقة:

> اسمك في الملعب. إنجازك متوثق داخل البطولة. وكارتك جاهز للفخر.

### 3.2 Frontend وعلم النفس

يرى الفريق أن دوافع الاستقلالية والكفاءة والانتماء أقوى من الضغط المصطنع، بما يتفق اتجاهيًا مع [نظرية التحديد الذاتي](https://www.selfdeterminationtheory.org/SDT/documents/2000_RyanDeci_SDT.pdf)&rlm;. الفخر المقبول هو فخر إنجاز مكتسب، لا إذلال للخصم أو ترتيب «أسوأ لاعب». كل نتيجة أو لقب يجب أن يعود إلى `MatchEvent` أو نتيجة معتمدة.

### 3.3 Backend والأمان والبيانات

أكدت اللجنة أن البطولة العامة والمميزة والمشاركة وClaim موجودة فعلًا، فلا نعيد بناءها. لكنها اكتشفت أن `analyticsEvents` كانت تسمح لكل مستخدم مسجل بالقراءة، وأن الكتابة العميلية أمكن إغراقها أو تزوير الـFunnel، وأن الـpayloads حملت IDs ثابتة. عولج الاحتواء في `ELR-SEC-105`، ولا يصبح القياس حقيقة قرار حتى ينفذ العقد الموثوق `ELR-OPS-405`&rlm;.

### 3.4 السوشيال ميديا

اقترح الخبير وظيفة مختلفة لكل قناة بوصفها فرضية اختبار:

- تستخدم مجموعات الدردشة للتحويل الخاص والدعوة وClaim&rlm;.
- يستخدم TikTok لاكتشاف قصة قصيرة حقيقية.
- يستخدم Instagram لهوية الفريق وبطاقات المفاخرة.
- يستخدم Facebook لبناء الثقة داخل المجتمعات المحلية.
- يستخدم QR جسرًا من الملعب إلى البطولة أو Claim&rlm;.

لا يعاد نشر محتوى المستخدم لأن صاحبه شاركه؛ إعادة النشر تحتاج موافقة عربية مستقلة ومحددة وقابلة للسحب. تدعم [إرشادات الموافقة الصادرة عن مركز حماية البيانات المصري](https://pdpc.gov.eg/assets/pdf-data/Guidelines/DSConsent.pdf) مبدأ الموافقة الصريحة والمعلومة والمحددة، مع متطلبات إضافية لبيانات الأطفال.

### 3.5 رئيس المشروع

حكم رئيس المشروع أن W1 وW2 وW4 هي المسار الحرج، وأن UX والبحث يمكنهما العمل بالتوازي إذا كانت السعة مستقلة. الـPilot لا يبدأ بعشر بطولات دفعة واحدة، بل يتوسع بعد كل بوابة تشغيلية.

## 5. القرارات النهائية

1. **الشريحة الأولى:** منظم بطولة بالغ ومتكرر؛ القائد واللاعب محركا التبني؛ المشاهد مدخل الحلقة.
2. **الوعد:** تشغيل بطولة حقيقية ثم تحويل الإنجاز المعتمد إلى فخر قابل للمشاركة وClaim&rlm;.
3. **North Star التشغيلية:** عدد البطولات التي تكمل داخل نافذة متفق عليها: مباريات مولدة ← أول نتيجة معتمدة ← Pride Preview أو Export ← فتح خارجي أو Claim صالح. يعرض كل جزء منفصلًا حتى لا يخفي Aggregate ضعيفًا.
4. **المسار الحرج:** الأمن والخصوصية وCI ثم UX ثم Android release؛ البحث فقط يعمل بالتوازي.
5. **لغة الشباب:** مصرية محترمة ومباشرة، بلا تعميم جيلي أو ابتذال أو ادعاء «رسمي».
6. **الفخر:** مستحق وقابل للتتبع، ولا توجد Shame mechanics أو Streaks أو ندرة مزيفة.
7. **النمو:** Organic Seed أولًا؛ لا Paid Ads أو Creator كبير قبل إثبات Activation والاحتفاظ.
8. **السوشيال:** يوزع محتوى البطولة الحقيقي خارج التطبيق؛ لا Social Feed أو Chat لخدمة خطة المحتوى.
9. **الخصوصية:** لا إعادة نشر UGC دون موافقة منفصلة، ولا PII أو أسماء داخل روابط القياس، ولا استنتاج منصة المشاركة من Android Sharesheet&rlm;.
10. **العمر:** لا استهداف لمن هم دون 18 في V1 قبل سياسة قُصّر وموافقة ومراجعة قانونية وفنية.

## 7. مبادئ UX القابلة للاختبار

1. يجد 90% من العينة الإجراء التالي خلال ثلاث ثوانٍ.
2. يميز 90% بين «مسجلة» و«مستنية اعتماد» و«معتمدة» خلال خمس ثوانٍ.
3. يكون تقاطع لاعبي الملعب والبدلاء صفرًا في كل Draft state&rlm;.
4. لا يزيد مسار اللاعب الزائر عن المسجل بأكثر من خطوة تشغيلية.
5. يصف 90% بدقة ما سيظهر قبل فتح Android Sharesheet&rlm;.
6. تعمل المهام الحرجة بيد واحدة وضوء نهار وشبكة بطيئة وtext scale ‏200%&rlm;.
7. لا يظهر ذهب أو لقب أو احتفال بلا دليل من مصدر الحقيقة.
8. لا يوجد مؤشر عام لـ«أسوأ لاعب» أو عقوبة انقطاع أو مقارنة مهينة.

هذه أهداف Usability Pilot وليست Benchmarks سوقية؛ تعدل بعد أول baseline موثق.

## 8. نوافذ فرضيات مشروطة وليست مواعيد تسليم

### نافذة 0–30: البحث والاحتواء

- يبدأ المسار الهندسي W1 ثم W2 بحسب البوابات والسعة، ويبدأ إصلاح CI بالتوازي عند توفر منفذ مستقل؛ لا تعد نافذة البحث موعدًا لإغلاق الموجتين.
- اكتمل احتواء القياس العميل في `ELR-SEC-105`؛ تدرس الحاجة إلى Data Dictionary خادمي لاحقًا ولا تصبح منصة Analytics شرطًا للبحث.
- تجري 12 مقابلة مع منظمين وقادة و6 ملاحظات تشغيل، موزعة قدر الإمكان بين القاهرة/الجيزة والدلتا والصعيد.
- تختبر ثلاث رسائل قيمة ونموذج دعوة واحدًا دون حملة عامة أو Paid Ads&rlm;.
- يتوقف التموضع إذا كان الألم الحاكم حجز الملعب أو تحصيل الأموال، لا التنظيم والتوثيق.

### نافذة 31–60: الجاهزية

- تغلق W3 وW4 وتختبر الأجهزة المتوسطة والمنخفضة والشبكة البطيئة.
- يثبت Signing وFirebase preflight وClosed Testing&rlm;.
- يحول البحث إلى Creative Matrix وResearch Decision Log، ولا يغير V1 بميزة جديدة دون تذكرة.
- لا يبدأ Pilot إذا لم تغلق بوابات الأمان والخصوصية والإصدار.

### نافذة 61–90: Pilot متدرج

- تبدأ دفعتان حقيقيتان، ثم ثلاث، ثم خمس فقط بعد نجاح كل بوابة.
- يتوقف التوسع عند فقد بيانات أو Claim خاطئ أو PII leak أو authorization regression أو High/Critical أو blocker في الحلقة.
- بعد أول دفعتين يعتمد المجلس baseline وحدود الاستمرار، بدل فرض نسب نمو من السوق النظري.
- لا يبدأ Paid Acquisition قبل ثبوت منظم أنشأ بطولة ثانية أو عاد لتشغيل حدث جديد في دورة زمنية واقعية.

إذا تأخرت بوابة تقنية، تتحرك النافذة التالية؛ لا تُختصر بوابة لتلحق تاريخًا.

## 9. Playbook السوشيال الأولي

### أعمدة المحتوى

- **اتوثق:** نتيجة أو هدف أو MVP معتمد.
- **اتفاخر:** بطل أو تأهل أو هداف أو Milestone حقيقي.
- **الطريق للكأس:** مجموعة أو شجرة أو Road to Final&rlm;.
- **الحارة بتنظم نفسها:** أثر التطبيق على الوضوح دون تحقير المنظم.
- **هوية الفريق:** شعار وتشكيلة ومباراة قادمة بموافقة أصحابها.
- **وشوش البطولة:** قصة قصيرة حقيقية بموافقة مستقلة.

### تقويم Seed لأربعة أسابيع

| :--- | :--- | :--- | :--- |

ينشر حساب الحريف ثلاث قطع تحريرية أسبوعيًا كحد Pilot، بينما يولد التطبيق اللحظات الحدثية عند وقوعها. لا محتوى يومي لملء التقويم.

## 10. القياس والحماية

### تعريفات القرار

- **منظم مفعّل:** أنشأ بطولة حقيقية، أضاف فريقين على الأقل، وولّد مباريات.
- **تحقق القيمة:** اعتمد أول نتيجة حقيقية.
- **حلقة الفخر:** ظهرت بطاقة حقيقية ثم بدأ المستخدم المشاركة أو التصدير.
- **حلقة النمو:** فتح رابط منسوب ثم اكتمل Claim صالح أو بدأت بطولة جديدة.

لا يُسمى الرجوع من Android Sharesheet «مشاركة مكتملة». يوضح [توثيق `share_plus`](https://pub.dev/documentation/share_plus/latest/share_plus/ShareResultStatus.html) أن النتيجة قد تكون غير متاحة حسب المنصة، كما أن [Android Intent](https://developer.android.com/reference/android/content/Intent#EXTRA_CHOSEN_COMPONENT_INTENT_SENDER) لا يضمن callback موحدًا يثبت وجهة أو اكتمال النشر.

### عقد القياس المستهدف

- يفصل Product Analytics عن Logs التشغيلية.
- لا يحمل event تحليلي `actorId`, `targetId`, `entityId`, `matchId`, `tournamentId` أو نصًا حرًا.
- يقتصر على enums وbuckets محدودة مثل `surface`, `result`, `durationBucket`, `networkStateBucket`, `participantKind`, `teamCountBucket`&rlm;.
- تستخدم Logs التشغيلية `requestId` محميًا وقصير الاحتفاظ عند الحاجة، ولا تصبح Funnel منتج.
- يخضع الإدخال الخادمي للحصص وdeduplication والاحتفاظ والحذف واختبارات spam&rlm;.
- حتى تنفيذ العقد، تتوقف كتابة وقراءة Analytics العميلية ولا تسجل parameters في logs&rlm;.

يفترض التخطيط فريقًا صغيرًا: Backend واحد، Frontend واحد، QA جزئي أو كامل، ورئيس مشروع وخبراء بحث ونمو جزئيون. الحد الأقصى مساران برمجيان متزامنان، وتذكرة P0 واحدة لكل مهندس، و20% من السعة للمراجعة والانحدار. التقدير يعاد بعد كل بوابة؛ لا يعتمد المجلس وعدًا زمنيًا ثابتًا قبل معرفة السعة الحقيقية.

### 12.1 توقيعات البوابات ومنع الاعتماد الذاتي

- تعتمد W1/W2 فقط بعد تنفيذ Backend، ومراجعة AppSec مستقلة، وإعادة اختبارات الهجوم بواسطة QA&rlm;.
- لا تغلق W2 أو `ELR-SEC-108` أو أي Analytics/SDK/Storage/Migration قبل جرد تدفقات البيانات وتوقيع مراجع هندسة الخصوصية على الإسقاط العام والحذف والاحتفاظ والإفصاحات.
- تعتمد W3 بعد تحقق Product من المهمة، وQA من الانحدار، وخبير تشغيل البطولات من الواقعية، ومراجع الوصول والأداء من قابلية الاستخدام الفعلية.
- لا تغلق W3 أو `ELR-REL-504/506` قبل أن يراجع خبير المحتوى العربي وRTL نصوص Claim والنزاعات والموافقات وPlay، وأن يثبت مراجع موثوقية Android الاستئناف وcached state وإعادة المحاولة بلا ازدواج على شبكة ضعيفة أو منقطعة.
- لا تعتمد هوية أو بطاقة مفاخرة أو فيديو أو أصل متجر جديد قبل مراجعة المدير الإبداعي لتماسك الهوية والمقروئية في المقاسات المستهدفة، وProduct لحقيقة الرسالة، وQA لجودة التصدير؛ وينضم المستشار القانوني عند وجود UGC أو صوت أو شعار أو أصل لطرف ثالث.
- تعتمد W4 بعد توقيع كبير الهندسة وAppSec وQA على CI والاعتماديات وسلسلة التوريد.
- لا ينفذ W5 أو نشر Firebase أو Play إلا بإذن `OWNER` وبعد توقيعات AppSec وQA وCloud Operations وAndroid/Play Release ومراجع هندسة الخصوصية، والقانون فيما يخص الخصوصية وData Safety&rlm;.
- لا تمر Claim أو بطولة عامة أو إعادة نشر UGC أو دفعة Pilot دون توقيع نزاهة المنصة على التبليغ والحظر والإزالة والاستئناف واحتواء الانتحال والإساءة.
- لا يصدر Product قرار `Continue / Adjust / Kill` للـPilot قبل أن يثبت خبير التحليلات تعريف المقاييس وصلاحية الاستنتاج، ويثبت قائد عمليات الـPilot وتشغيل البطولات والدعم أن النتيجة لم تعتمد على تدخل يدوي غير مسجل، وتوقع نزاهة المنصة سلامة الموافقات والإشراف؛ بعد ذلك يأذن `OWNER` بالاستمرار التشغيلي.
- إذا كان الفريق صغيرًا واضطر شخص لتغطية أكثر من مقعد، يعين مراجع خارجي مستقل للموافقة الحساسة بدل إسقاط البوابة.

### 12.2 خبرات مؤجلة أو غير لازمة كمقاعد V1

- لا يضاف مقعد iOS لأن Android هو نطاق الإصدار الحالي.
- لا تضاف مقاعد Fantasy أو AI/ML أو Monetization لأن هذه المسارات خارج V1&rlm;.
- يراجع خبير مالية وتسعير أو شراكات قبل أي Paid Acquisition أو نموذج إيراد، لا قبل إثبات التفعيل والاحتفاظ.
- تستخدم خبرات Firestore المتخصصة وCI/CD وData Engineering واختبار الأجهزة كمنفذين حسب التذكرة، تحت أصحاب القرار السابقين. ويبقى مراجع المحتوى العربي وRTL ومراجع موثوقية Android بوابتي مراجعة عند أثرهما، لا مقعدين دائمين.
