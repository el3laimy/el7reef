# جرد بيانات V1 ومصفوفة الاحتفاظ وورقة Data Safety

**الحالة:** جاهز للمراجعة المشتركة بين `OWNER` و`ENG`  
**آخر تحديث:** 12 يوليو 2026  
**النطاق:** تطبيق Android، Firebase، صفحات الويب العامة، والبيانات المحلية في V1&rlm;.

هذه الوثيقة تصف السلوك الموجود في الكود، ولا تُعد موافقة قانونية أو إرسالًا مكتملًا إلى Google Play. كل بند يحمل `OWNER-VALIDATE` يحتاج قرارًا صريحًا قبل الإرسال.

## 1. ملخص تنفيذي

- يعتمد تسجيل الدخول على Google وFirebase Authentication&rlm;.
- يخزن Firestore الحسابات والفرق والبطولات والمباريات ومرجعية أحداث المباريات والعلاقات والبلاغات وسجلات التدقيق.
- يخزن Firebase Storage صور البروفايل فقط تحت `profiles/{uid}/`&rlm;.
- يسجل التطبيق أحداث استخدام محدودة داخل `analyticsEvents`، ولا يستخدم حاليًا Firebase Analytics SDK&rlm;.
- يستخدم Crashlytics لتشخيص الأعطال وRemote Config لبوابات الميزات.
- لا يجمع V1 الموقع أو جهات الاتصال أو الرسائل أو البيانات المالية أو الصحية.
- بيانات اللاعب أو الفريق الزائر قد تتضمن اسمًا وصورة ووسيلة تواصل اختيارية يضيفها المنظم؛ لذلك تُعامل كبيانات شخصية حتى قبل إنشاء حساب.

## 4. مصفوفة الاحتفاظ والحذف

| البيانات | الاحتفاظ الحالي | عند حذف الحساب | القرار أو الفجوة |
| :--- | :--- | :--- | :--- |
| Firebase Auth | حتى حذف الحساب | حذف مستخدم Auth بعد إعادة التأكيد | مكتمل محليًا؛ النشر ينتظر Blaze |
| ملف `players/{uid}` | أثناء وجود الحساب | حذف recursive | مكتمل محليًا |
| صور `profiles/{uid}/` | حتى الاستبدال أو الحذف | حذف كل الملفات تحت المسار | مكتمل محليًا |
| العلاقات والإشعارات والدعوات الخاصة | بلا TTL عام | حذف الوثائق المرتبطة بالمعرّف | مكتمل في خطة الحذف |
| نتائج المباريات والبطولات | غير محددة المدة | تبقى للحفاظ على النزاهة مع استبدال المعرّف بـ`deleted-{hash}` | `OWNER-VALIDATE`: اعتماد مدة الاحتفاظ القانونية |
| `auditEvents` وسجلات النزاع | غير محددة المدة | فصل `actorId` عن الحساب؛ حذف النزاعات التي رفعها المستخدم وفق الخطة الحالية | `OWNER-VALIDATE`: هل يلزم الاحتفاظ بالنزاع بعد إزالة النص الشخصي؟ |
| `analyticsEvents` | لا يوجد TTL حاليًا | فصل `actorId` إن وجد | مطلوب إضافة TTL أو مهمة purge؛ الاقتراح 90 يومًا يحتاج OWNER |
| رموز المطالبة | لها expiry/status لكن لا يوجد TTL حذف مثبت | تحذف الرموز التي أنشأها الحساب | مطلوب purge دوري للرموز المنتهية |
| بيانات الزوار ووسائل التواصل | لا يوجد TTL آلي | لا ترتبط دائمًا بحساب يمكنه حذفها | `OWNER-VALIDATE`: اعتماد قناة حذف ومدة؛ مقترح حذف وسيلة التواصل بعد claim أو نهاية البطولة + 30 يومًا |
| تقارير `userReports` | لا يوجد TTL آلي | تبقى كسجل أمان مع استبدال معرّف المُبلّغ أو الهدف المحذوف بالمعرّف المجهّل | مطلوب سياسة retention وحقول resolution |
| Crashlytics | وفق إعدادات Firebase/Google | لا يملك التطبيق حذفًا فرديًا مباشرًا | `OWNER-VALIDATE`: مراجعة إعدادات الاحتفاظ في Firebase ووصفها في Play |
| مسودة النتيجة المحلية | حتى submit أو discard أو استبدال البصمة | تزول مع بيانات التطبيق؛ لا يشملها callable | مقبول وظيفيًا، ويجب ذكر التخزين المحلي عند الحاجة |
| ملفات المشاركة المؤقتة | وفق نظام التشغيل وحزمة المشاركة | لا توجد نسخة دائمة في خادم الحريف | تحقق جهاز مطلوب |

## 5. خريطة حذف الحساب المنفذة

تنفذ الدالة `deleteAccountData` الخطوات التالية:

1. تكتب طلبًا بمعرّف مجهّل ثابت، ولا تستخدم UID الخام كمفتاح سجل الاحتفاظ.
2. تحذف صور Storage وملف اللاعب والبيانات الخاصة والعلاقات.
3. تزيل UID من مصفوفات الفرق والمباريات.
4. تستبدل ملكية السجلات التاريخية بمعرّف `deleted-{sha256-prefix}`&rlm;.
5. تحذف مستخدم Firebase Authentication&rlm;.
6. تعيد نتيجة idempotent عند غياب مستخدم Auth في إعادة المحاولة.

لا تُعد هذه العملية منشورة في الإنتاج حتى تنجح بوابة Blaze وsmoke test على المشروع المستهدف.

### خصائص الأمان والإفصاح

- النقل مشفر عبر HTTPS وخدمات Firebase&rlm;.
- حذف الحساب متاح داخل التطبيق وصفحة ويب عامة.
- لا تُباع البيانات الشخصية.
- مشاركة بطاقات المفاخرة فعل يختاره المستخدم إلى تطبيق خارجي.
- لا يوجد إعلان أن التطبيق موجه للأطفال؛ القرار العمري والتصنيف يحتاجان `OWNER-VALIDATE`&rlm;.
- يجب مراجعة قسم Data Safety بعد بناء AAB النهائي لأن SDKs المدمجة، لا `pubspec.yaml` فقط، هي الدليل الحاسم.

## 7. قرارات OWNER المطلوبة قبل الإرسال

1. اعتماد مدد الاحتفاظ لنتائج المنافسة والتدقيق والبلاغات والقياس.
2. اعتماد سياسة بيانات اللاعب الزائر ووسيلة التواصل وحقه في الحذف.
3. تعيين مسؤول مراجعة البلاغات ووقت استجابة معلن داخليًا.
4. مراجعة إعدادات Crashlytics وGoogle Firebase Data Processing&rlm;.
5. تحديد الفئة العمرية والجمهور المستهدف والتصنيف.
6. اعتماد إجابات “Collected/Shared/Ephemeral/Optional” داخل Play Console بعد فحص AAB&rlm;.
